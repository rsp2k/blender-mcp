The add-on has a **Chat** tab in the 3D Viewport sidebar. Type what you want ("put a 2 m cube on the table and box it so I can see it") and a model does it in the Blender you typed in, using the same tools an external MCP client would. Nothing else needs to be installed.

The conversation runs on the server, not in Blender. The add-on sends your message as an ordinary MCP tool call over the connection it already has; the server asks the model, runs the tools it picks against your Blender, and streams progress back into the panel. Your API key, if you use one, is stored on the server encrypted and never kept in Blender's preferences file.

## Pick a backend

Open **Edit › Preferences › Add-ons › Blender MCP › Chat backend**:

| Backend | What you need | Notes |
|---|---|---|
| Shared GPU gateway | Nothing; it's the default | The server's own backend: open models on the operator's GPUs (qwen3 by default), unless the operator has set a different server default (below). One conversation turn at a time per account. |
| Claude API | Your Anthropic API key | `claude-opus-5` by default; any Claude model name works, e.g. `claude-opus-5-5`. |
| OpenAI-compatible | A base URL, a model name, and a key if the endpoint needs one | Ollama, LiteLLM, vLLM, or a hosted OpenAI-style API. The URL must be reachable from the server. |

Press **Save backend**. The key is sent once to the server and the field clears. To change it, enter a new one; to remove it, choose **Clear backend**.

### The server default

Accounts that haven't saved a Claude key or an OpenAI-compatible URL use the server's default backend. It is normally the GPU gateway, but the operator can point it elsewhere, for example at Claude with the server's own key while the local models are paused (`CHAT_DEFAULT_PROVIDER=anthropic` plus `ANTHROPIC_API_KEY`; the model defaults to `claude-opus-5`, or `CHAT_DEFAULT_MODEL`). A backend you saved yourself always wins. The **Current:** line in the preferences says `server default` when you are on it; the server's key is never sent to Blender. `CHAT_GATEWAY_USERS`, when set, limits the server default to the listed accounts, whichever provider it is.

With Claude (your key or the server's), `look_at_viewport` sends the screenshot to Claude itself rather than to the gateway's vision model. Claude calls think adaptively between tool steps, and requests Claude declines are re-run on Anthropic's recommended fallback model where the API supports it (`CHAT_ANTHROPIC_FALLBACKS`, on by default); a request that is still declined ends the turn with a message naming the refusal category. `CHAT_ANTHROPIC_EFFORT` (`low` to `max`) sets the effort level; unset leaves the API's default.

<Aside type="caution">
With the OpenAI-compatible backend, the base URL is fetched by the server, not by your computer, so `http://localhost:11434` means the server's localhost. Use an address the server can reach.
</Aside>

## Approvals

The model can run Python in your Blender only after you allow it. When it wants to, the Chat tab shows the code and **Allow** / **Deny**. Deny (or no answer within two minutes) tells the model you declined, and it carries on without it. Deleting objects asks the same way.

## What the model can do

A curated set of tools, not all of them: scene and object info, framing the view, looking at the viewport (a vision model describes a screenshot, annotations included), annotating objects, creating meshes and placing them, materials, viewport shading, a quick render from an axis, mesh checks, and Python behind an approval. The set is chosen on the server and may grow.

## The transcript

Recent messages show in the panel. The full conversation, including each tool the model ran, is written to a Blender text block named **BlenderMCP Chat**; **Open log** shows it in a Text Editor. It is saved with your .blend like any text block.

## Wire contract

This is the interface between the add-on and the server, for anyone building another client.

### `blender_chat` (add-on role only)

```text
blender_chat(message: str, history: list[{role: "user"|"assistant", content: str}] | None)
```

- The server targets the Blender whose add-on made the call; there is no `target_uuid` argument.
- `history` is the recent conversation, text only, at most 20 entries. The server keeps no conversation state.
- The call is long-running (up to the server's turn limit, 5 minutes by default). Progress arrives as MCP progress notifications on the call; each `message` is a JSON object:

```json
{"t": "status", "text": "Thinking…"}
{"t": "tool", "name": "create_mesh", "phase": "start"}
{"t": "tool", "name": "create_mesh", "phase": "end", "ok": true, "ms": 412, "head": "{\"object\": \"Table\", …"}
{"t": "tool", "name": "execute_code", "phase": "end", "ok": true, "ms": 4310, "wait_ms": 81200}
{"t": "tool", "name": "add_primitive", "phase": "end", "ok": false, "ms": 3, "error": "{\"status\": \"error\", \"error\": \"invalid_argument\", …"}
{"t": "text", "text": "Added a 2 m cube named Table…"}
```

- `ms` is the tool's own time. `wait_ms` appears only when the step asked for approval, and is the time spent waiting for the user.
- A failed step carries `error`, the start of its error text (at most 300 characters, whitespace collapsed), so a fast argument rejection can be told from a failure inside Blender. A successful step carries `head`, the first 160 characters of its result. Both are optional: clients must not require them. The add-on keeps them on the step's transcript entry and writes a failed step's `error` to the chat log.
- The result is a JSON string:

```json
{"status": "ok", "reply": "…", "steps": [{"tool": "create_mesh", "ok": true, "ms": 412, "head": "…"}], "elapsed_s": 9.8,
 "backend": {"provider": "gateway", "model": "qwen3"}}
```

- Other statuses: `disabled` (chat is off on this server), `no_backend` (the gateway isn't available to this account and no backend is configured; `hint` says what to do), `busy` (a turn is already running for this account), `backend_error` (the model call failed; `detail` has the reason), `timeout`. `backend_error` and `timeout` also carry `steps`, `elapsed_s` and `backend` for whatever ran before the failure, and `timeout` carries the `reply` so far (often empty).
- Problems with the call itself come back as `{"status": "error", "error": …}`: `not_registered` (this session hasn't called `blender_register_client`, so there is no Blender to target), `empty_message`, `unauthenticated`.

### Approvals are MCP elicitation

For a tool that needs approval, the server sends an `elicitation/create` request on the same session while the call is running. The message starts with `BlenderMCP approval:` and the requested schema has no fields, so the client answers **accept** (allow) or **decline** (deny). Clients should decline elicitations they don't recognise. Unanswered requests are declined by the server after 120 seconds.

<Aside type="caution">
The MCP Python SDK runs a client's elicitation callback inside the session's receive loop, so while an approval is waiting that session reads nothing else: no progress, no replies to other calls, no keepalives. Answer (or auto-decline) promptly, and don't let a stream-silence watchdog reconnect the session while a prompt is showing.
</Aside>

### `blender_set_chat_backend` (add-on role only)

```text
blender_set_chat_backend(provider: "gateway"|"anthropic"|"openai", model: str | None = None,
                         base_url: str | None = None, api_key: str | None = None, clear: bool = False)
```

Returns `{"status": "ok", "backend": {"provider", "model", "base_url", "has_key", "source"}}`, where `source` is `user` for a backend the account saved and `server` for the server default (then `has_key` says whether the server has a key for it); no key, the account's or the server's, is ever returned. Omitting `api_key` keeps the saved key when the provider stays the same; an empty string removes it. Refusals are `{"status": "error", "error", "detail"}` with `error` one of `invalid_provider`, `invalid_argument`, `api_key_required`, `secret_key_not_configured`. `blender_get_chat_backend()` returns the same shape. Arguments to this tool are never recorded by the server's call logging.

### Feature flag

When chat is enabled, the result of `blender_register_client` includes `"features": ["chat"]`. The add-on shows the Chat tab only then.
